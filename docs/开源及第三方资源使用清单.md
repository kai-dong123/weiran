## 一、上游开源项目

| 名称 | 类型 | 版本 / 来源 | 许可证 | 使用方式 | 关键许可义务 | 自研边界 |
|---|---|---|---|---|---|---|
| MiroFish | 开源软件（多智能体社交仿真引擎） | commit `39d849138ef254f6c737ab4c4705e5545dbe31d4`<br>https://github.com/666ghj/MiroFish | AGPL-3.0 | **本项目基于其二次开发**：沿用上游「OASIS 多智能体仿真 + 角色画像 → 推演驱动 → 知识存储」的整体管线。其中**逐字复用**两处（可用动作列表、profile 格式定义），**重写**三处（驱动脚本、记忆存储、前端），**新增**一处自研核心（六维世界状态引擎 + 闭环回注）。逐项见下方对照表 | 保留版权与许可声明；衍生作品同样以 AGPL-3.0 发布；向网络用户提供完整对应源码 | 见第三节 |

**「二次开发」与「复用了哪几处」不是两种说法，是两个层次。** 需要同时说清，
缺一个都不准确：

- **关系层（定性）**：本项目的整体架构来自上游 —— 用 OASIS 跑多智能体社交仿真、
  用角色画像喂 agent、用一个驱动脚本逐轮推进、把结果存进知识层。这个骨架是上游的，
  因此本项目是它的**衍生作品**，依 AGPL-3.0 发布。
- **代码层（定量）**：在 AGPL 的判定里，**衍生关系不取决于是否逐字复制**——
  改写过的衍生作品仍然是衍生作品。所以不能因为「没整份搬文件」就自称取用极少；
  反过来，说清改写了哪些，也不改变它是衍生作品这个定性。
- **下面这张表是「改写了什么」，不是「关系有多浅」**：

| 上游部件 | 本项目的处置 | 依据 |
|---|---|---|
| 可用动作列表（`TWITTER_ACTIONS` / `REDDIT_ACTIONS`） | **逐字复用** | `simulate.py:57-67`，注明上游 `run_parallel_simulation.py:178-202` |
| profile 格式（CSV 表头与语义） | **逐字对齐** | `profiles.py:145-155`，注明上游 `oasis_profile_generator.py:1139` |
| 推演驱动 `run_parallel_simulation.py` | **重写**（自研批式驱动） | `simulate.py:1-25`，理由见下 |
| 记忆存储（上游硬锁 Zep Cloud） | **替换**为本地 SQLite + FTS5 | `store.py:1-25` |
| Web 端前端与实时命令下发 | **去掉**（本项目 CLI 优先） | 见第三节末 |
| 六维世界状态引擎 + 闭环回注 | **新增**（本项目自研核心） | `world_state.py` / `perception.py` |

**为什么驱动脚本要重写而不是整份搬上游那份。** 上游 `run_parallel_simulation.py` 共 1699 行，其中真正与 OASIS 交互的不到三分之一，其余是给「Web 端实时下发命令」准备的：IPC 命令目录轮询、`env_status` 心跳、等待命令循环、双平台并行、信号处理。本项目是**批式推演**——跑一轮、拿动作、推进世界状态、再跑下一轮——那套常驻机制是纯粹的负重。更硬的理由是：**世界状态引擎必须逐轮拿到动作**，而上游把动作写进 OASIS 自己的 SQLite 就不再管了。这个逐轮闭环是自研核心，夹在别人的驱动里会很别扭。（上游那套的用途是让人在网页上对正在跑的 agent 做访谈；本项目保留 `ManualAction` 做**事件注入**，效果相同而实现简单得多。**注意：重写驱动不改变衍生作品的定性**，只影响「改了哪一部分」的描述。）

出处：`backend/weiran/simulate.py:1-25`（模块 docstring 即上述理由）、`:57-67`（动作列表及其上游行号）。

## 二、第三方依赖与服务

| 名称 | 类型 | 版本 | 许可证 / 授权 | 使用方式 | 关键义务或限制 | 合规状态 |
|---|---|---|---|---|---|---|
| camel-oasis | Python 库 | 0.2.5 | **Apache-2.0**（随包 `licenses/LICENSE` 实读确认） | 多智能体社交平台仿真内核 | **版本锁定，不可升级**——上游驱动对 oasis 内部做了 monkey-patch，版本一变就碎 | ✅ 已核实 |
| camel-ai | Python 库 | 0.2.78 | **Apache-2.0**（随包 `licenses/LICENSE` 实读确认） | 模型接入层 | 版本锁定。另注：它对 `mcp` 的上界开放，pip 会解析到 2.x 而 `FastMCP` 已移出 `mcp.server`，因此 `requirements.txt` 必须补 `mcp<2` | ✅ 已核实 |
| DeepSeek API | 模型服务 | 模型 id `deepseek-flash` | 服务条款 | 系统全部 LLM 调用（归类、推演、抽取） | 遵守其服务条款与使用政策 | ✅ 已实测打通 |
| `Twitter/twhin-bert-base` | 模型权重（HuggingFace） | 未固定版本（`from_pretrained` 取 main） | **许可证待核实** | `camel-oasis` 内置的 Twitter 推荐系统用它算帖文相似度（`oasis/social_platform/recsys.py`）。本地缓存后离线加载，不再联网 | 首次运行需联网下载约 **1.1 GB**；无缓存时每轮会先等一次超时重试（见下） | ⚠️ 许可证待核实 |
| 嵌入模型 | 模型服务 | 未接线 | — | 向量检索 | 向量列与检索通路已就位，**默认关闭**（见下） | 未启用 |

> **版本锁定是刻意的，不是懒。** `requirements.txt` 与 `pyproject.toml` 里对仿真内核写死版本，
> 并在 README 中说明「请勿单独升级」——这不是保守，是因为升级会静默改变仿真行为。

> **推荐系统那个模型是一个运行期外部依赖，藏在上游库里。** `camel-oasis` 的 Twitter
> 平台默认用 `Twitter/twhin-bert-base` 算帖文相似度，第一次跑会向 `huggingface.co`
> 下载约 1.1 GB。它还带来一个**每轮都发生的浪费**：`huggingface_hub` 哪怕模型已在
> 本地缓存，也会先发一个 HEAD 校验请求，失败要重试 5 次 —— 实测**每轮白等约 127 秒**
> （第 1 轮墙钟 134.1s，其中 LLM 只占 7.2s）。因此本项目在拉起源码之前先探测本地缓存，
> 缓存完整就置 `HF_HUB_OFFLINE` / `TRANSFORMERS_OFFLINE`（`simulate.enable_hf_offline_if_cached`，
> 11 条测试）。修后同一条 15 轮推演全程 **110.7 秒**。

> **嵌入通路的状态要说清楚**：`store.py` 有向量列与 `search_vector()`，但**没有调用嵌入服务的客户端**，
> 因此该通路当前跑不出向量。语料仅 33 个 chunk 的规模下，混合检索不会带来可测量的召回提升，
> 所以只保留词法与向量两条**独立**通路，不做融合——这一点在技术报告中如实写明，而不是假装做了。

> **本清单不含 Flask。** 本项目是 CLI 优先，不提供 Web 服务，因此不声明 Web 框架依赖。
> 项目取向是「每少一个依赖，就少一个『装不上』的失败点」。

> AGPL-3.0 第 13 条：本项目若以网络服务形式对外提供，须向使用者提供完整对应源码。
> 本项目公开发布于代码托管平台，满足该义务。
